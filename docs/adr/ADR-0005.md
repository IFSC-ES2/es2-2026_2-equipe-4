# ADR-0005: Autenticação JWT e leitura pública dos projetos

## Status

**Aceita.** Implementada na Sprint 2. Complementa a
[ADR-0004](ADR-0004.md).

## Contexto

Na vitrine, visitantes devem consultar projetos sem conta, mas a publicação
precisa ser associada a um usuário cadastrado. O front-end e a API são
componentes separados, comunicando-se por HTTP.

## Decisão

Usar Spring Security com sessão sem estado e token JWT. Cadastro e login são
públicos; `POST /auth/login` devolve o token. As rotas `GET /projetos` e
`GET /projetos/{id}` são públicas. O envio de arquivo e metadados exige
`Authorization: Bearer <token>`. O token contém o e-mail como subject; no
envio de metadados, o servidor consulta o usuário e define `autorId`, sem
confiar no valor recebido no corpo da requisição.

## Alternativas aplicáveis

| Alternativa | Consequência |
|---|---|
| Permitir publicação anônima | Não estabeleceria a autoria autenticada exigida pelo produto. |
| Sessão mantida no servidor | Exigiria estado de sessão entre requisições e outra configuração de autenticação para a interface separada. |
| JWT sem sessão no servidor | Simplifica a autenticação HTTP entre front-end e API, mas exige proteção do segredo, expiração e cuidado com o token no cliente. Escolhida. |

Não há registro de votação formal dessas alternativas; a tabela explicita
os trade-offs da decisão implementada.

## Consequências

- Consultas públicas e escrita autenticada são testadas separadamente; uma
  falha de autenticação deve produzir resposta 401.
- O front-end guarda o token em `localStorage` e o envia nas requisições
  protegidas. Esse armazenamento exige atenção à segurança do cliente.
- O segredo JWT e as credenciais de desenvolvimento ainda precisam ser
  retirados de valores fixos, conforme o [registro de riscos](../riscos.md)
  e a [issue #100](https://github.com/IFSC-ES2/es2-2026_2-equipe-4/issues/100).
