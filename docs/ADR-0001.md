# ADR-0001: Arquitetura do Projeto

## Status

**loading**

## Contexto

O projeto terá uma arquitetura em camadas, tanto em nível de sistema quanto em nível de aplicação.

Em nível de sistema, será adotada uma arquitetura tradicional composta por:

**Front-end → API → Banco de dados**

Essa abordagem é amplamente utilizada, possui baixa complexidade de implementação e facilita a evolução, integração e manutenção do sistema.

Todos os serviços serão disponibilizados em containers, utilizando Docker, com o objetivo de facilitar o desenvolvimento e permitir a execução e o deploy do projeto em diferentes ambientes.

A arquitetura foi escolhida principalmente com base na experiência prática dos integrantes do grupo, na facilidade de evolução e na integração entre as diferentes partes do sistema.

O sistema não precisará ser executado em um único ambiente. A utilização de containers permite minimizar problemas relacionados a diferenças de configuração entre ambientes de desenvolvimento e execução. Dessa forma, as principais exigências para executar o sistema serão apenas as ferramentas necessárias para a execução dos containers.

O MVP tem como objetivo entregar um sistema funcional, atendendo às funcionalidades descritas na Entrega 1. Além disso, busca-se garantir a reprodutibilidade do projeto e seu funcionamento em qualquer ambiente que atenda aos requisitos necessários para executar os containers.

As principais decisões foram tomadas considerando a experiência e as práticas dos integrantes do grupo, priorizando um baixo nível de complexidade para reduzir possíveis impedimentos durante o desenvolvimento e facilitar a resolução de problemas.

## Decisão

Será adotada uma arquitetura em camadas, separando o sistema em três componentes principais:

```text
┌──────────────┐
│  Front-end   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│     API      │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Banco Dados  │
└──────────────┘
```

O **front-end** será responsável pela interface e interação com o usuário.

A **API** será responsável pela implementação das regras de negócio e pela comunicação entre a interface e o banco de dados.

O **banco de dados** será responsável pela persistência das informações utilizadas pelo sistema.

A comunicação entre as camadas será realizada de maneira organizada, evitando que uma camada acesse diretamente responsabilidades pertencentes a outra.

Além da separação lógica das camadas, os serviços serão executados utilizando **containers Docker**, permitindo maior isolamento e reprodutibilidade entre ambientes.

A organização inicial do projeto seguirá uma separação entre front-end e back-end:

```text
projeto/
│
├── frontend/
│
├── backend/
│
├── database/
│
└── docker-compose.yml
```

A estrutura apresentada representa uma organização inicial e poderá ser ajustada durante o desenvolvimento conforme as necessidades do MVP.

## Alternativas consideradas

| Alternativa                                           | Vantagens                                                                      | Desvantagens                                                                                | Motivo da rejeição                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Arquitetura monolítica sem separação clara de camadas | Menor complexidade inicial e desenvolvimento rápido                            | Maior acoplamento entre componentes e maior dificuldade de manutenção                       | Apesar da simplicidade inicial, poderia dificultar a evolução e manutenção do sistema                    |
| Arquitetura baseada em microsserviços                 | Alta independência entre serviços e possibilidade de escalabilidade individual | Maior complexidade operacional, de comunicação, configuração e deploy                       | Complexidade desnecessária para o escopo e objetivo do MVP                                               |
| Execução sem containers                               | Configuração inicial mais simples                                              | Maior dependência do ambiente local e maior possibilidade de inconsistências entre máquinas | A utilização de containers oferece maior reprodutibilidade e facilita a execução em diferentes ambientes |

## Consequências

Inicialmente, algumas das tecnologias e componentes escolhidos podem apresentar maior complexidade e verbosidade durante a configuração. Entretanto, após a configuração inicial, a estrutura adotada facilita o crescimento e a evolução da aplicação.

A utilização de uma arquitetura em camadas também permite que alterações em uma determinada parte do sistema tenham menor impacto sobre as demais camadas.

Além disso, a utilização de containers facilita a reprodução do ambiente de desenvolvimento e execução, reduzindo problemas relacionados às diferenças entre ambientes.

A separação entre as responsabilidades também facilita a manutenção e permite que determinadas tecnologias sejam substituídas futuramente sem exigir uma reestruturação completa do sistema.

### Consequências positivas

* A separação entre front-end, API e banco de dados facilita a manutenção do sistema.
* A arquitetura permite adicionar novas funcionalidades sem alterar necessariamente todas as camadas.
* A utilização de containers facilita a reprodução do ambiente em diferentes máquinas.
* A organização em camadas facilita a substituição ou alteração de tecnologias no futuro.
* A estrutura adotada possui baixa complexidade para as necessidades atuais do MVP.
* A arquitetura permite que o projeto evolua futuramente sem exigir uma reestruturação completa.

### Consequências negativas ou riscos

* Existe um risco de aumento da complexidade durante a configuração inicial das tecnologias.
* A utilização de múltiplas tecnologias exige que os integrantes compreendam como as diferentes camadas se comunicam.
* A configuração dos containers pode exigir conhecimento adicional de Docker.
* Algumas decisões tomadas para simplificar o MVP podem precisar ser revistas caso o sistema cresça significativamente.

## Ações necessárias

* Definir a comunicação entre front-end e API.
* Definir a comunicação entre API e banco de dados.
* Criar a configuração dos containers.
* Validar a execução de todos os serviços utilizando containers.
* Criar uma configuração que permita reproduzir o ambiente de desenvolvimento de forma simples.
* Validar a integração entre as diferentes camadas.

## Relação com o MVP

O MVP tem como objetivo entregar um sistema funcional que atenda às características e funcionalidades definidas para a primeira entrega.

As decisões arquiteturais apresentadas neste documento servem como uma ponte entre os requisitos do problema e a solução implementada.

A prioridade nesta etapa é garantir o funcionamento das funcionalidades principais, evitando a introdução de complexidades que não sejam necessárias para o MVP.

A arquitetura adotada permite que o sistema seja desenvolvido de maneira organizada, reproduzível e com possibilidade de evolução em versões futuras.
